## 一、什么时候用(触发特征)

接口能打通,但**回包看不懂**:

- 回包 base64 解出来还是乱的 → 多半还有一层 AES/DES
- 回包是一串 hex,长度是 16 的整数倍 → 分组加密候选
- 请求要带 `sign` / `signature` / `token` / `timestamp` / `nonce` / `_csrf` → 签名层
- 回包字段全变但结构相同 → 流密码或 XOR
- `#EXTM3U` 拿不到,地址本身也是密文 → 取流层加密

**别急着上手解** —— 先用 `ZakaCrackKit.Probe` 定性(第 4 节),定性错了全白干。

## 二、五步走(原库流程 → ZAKA 版)

### 第 1 步 · 抓包定型(`re-netcap`)

先看清「谁和谁、发几帧、什么形状」,比直接猜算法快十倍:

```bash
# 会话列表:谁和谁说话、包数、字节数
tshark -r cap.pcap -q -z conv,tcp
# 每帧长度分布 —— 固定长度 = 定长消息;连续变化 = 变长(要找 framing)
tshark -r cap.pcap -T fields -e tcp.len | sort -n | uniq -c
# 找规律性心跳(每 30s 一个固定小包)
tshark -r cap.pcap -q -z io,stat,1
```

**抓包落点选择(ZAKA 场景)**:
- 网页站 → 浏览器 F12 的「Copy as cURL」直接拿全量请求头(最快,省掉抓包)
- App → 卡05 的 Frida hook 打 `okhttp3` / `HttpURLConnection` / `NSURLSession`,直接拿明文
- 有代理的 → 走本机已有转发层,别新造

### 第 2 步 · 判算法(`re-crypto-id`)

**常量表指纹**(最硬的判据):

```python
data = open('sample.bin','rb').read()
sigs = {
  'AES_SBOX':      bytes.fromhex('637c777bf26b6fc53001672bfed7ab76'),
  'CRC32_TAB_BE':  bytes.fromhex('0000000077073096ee0e612c990951ba'),
  'CRC32_TAB_LE':  bytes.fromhex('00000000963007772c610eeeba510999'),
}
for name, sig in sigs.items():
    i = data.find(sig)
    while i != -1:
        print(f"{name} @ 0x{i:x}"); i = data.find(sig, i+1)
```

**熵分析定位密文区**:

```python
import math, collections
for base in range(0, len(data), 4096):
    blk = data[base:base+4096]
    if not blk: break
    c = collections.Counter(blk); n = len(blk)
    h = -sum((v/n)*math.log2(v/n) for v in c.values())
    if h > 7.0: print(f"0x{base:x}: entropy={h:.2f}  <- 密文/压缩候选")
```

**单字节 XOR 速扫**(成本极低,必做):

```python
for key in range(256):
    dec = bytes(b ^ key for b in data)
    if sum(1 for b in dec if 32 <= b < 127) > len(data)*0.6:
        print(f"XOR key=0x{key:02x}")
```

**长度规律速判**:
- 密文长度**总是 16/32 字节整数倍** → 分组加密(先按 AES 试)
- 密文长度**跟明文一致** → 流密码(RC4 / ChaCha / XOR)
- **同页两次请求 key 就变** → 密钥现页现抓(黄仓那次的 `mvarr['10_1']` 就是这类)

> 静态只能给候选。**关键判据是明文长度与密文长度的关系**,这条比任何指纹都稳。

### 第 3 步 · 取密钥(`re-crypto-keys`)

按密钥**存在哪**分四个方向找:

| 密钥位置 | 怎么拿 |
|---|---|
| **页面内联**(HTML/JS 里写死) | 直接搜 32/16 位 hex、`key=`、`secret`、`iv=`;或从页面变量(如 `tk` 字段)现页现抓 |
| **前端 bundle 里**(打包进 JS) | 卡03 让 bundle 变可读,再搜常量 |
| **App 的 so 层** | 卡04 native 分支 + 卡05 Frida hook 加密函数出参 |
| **服务端下发**(接口取 key) | 跟一条取 key 的接口,注意它自己可能也带签名 |
| **动态生成**(每页/每会话变) | 必须还原生成算法,不能快照 —— 记「密钥怎么来的」而不是「密钥是什么」 |

**难点提醒**:密钥可能不叫 key,叫 `tk` / `salt` / `aid` / `ver` / 或者是个拼出来的字符串(`prefix + date + suffix`)。**搜名字找不到就搜"用途"** —— 找加密函数的入参。

### 第 4 步 · 解密实施(`re-crypto-decrypt`)

先定性、再动手(省时间的关键):

```python
from zaka_crack_kit import Cipher, Codec, Probe
```

- **`Cipher` 已覆盖**:AES 四模式(CBC/ECB/CTR/CFB)、DES/3DES、Fernet、**候选池回推密钥**
- 模式不知道 → 挨个试,CBC 还要猜 IV(常见:`key` 复用、全 0、密文前 16 字节)
- 填充不对 → 试 PKCS7 / zero / 无填充
- **解出来是明文但字段对不上** → 多半是**先压缩再加密**(zlib/gzip),加一层解压

**闭环验证(必做)**:解出的明文要能**解释业务** —— 拿到片名/地址/ID 才算成。
只报「解出来了」但没人看懂 = 没解出来。

### 第 5 步 · 签名层还原(`re-proto-rev` 的签名分支)

带 `sign` 的接口,顺序是:

1. **列全所有非手工字段** —— 页面上自动生成的参数一个都不能漏(漏一个就永远对不上)
2. **找签名函数的入参拼接顺序** —— 参数**排序方式**(字典序 / 按字段名 / 按出现顺序)是最常错的一处
3. **试常见算法** —— `md5(query + key)`、`hmac-sha256(body, key)`、`md5(json + timestamp + key)`
4. **时钟校准** —— 带时间戳签名的站,**先拿响应头 `Date` 校服务器时钟**(本机差几秒就全挂)
5. **对齐验证** —— 用自己算的 sign 打一发,服务端认了才算成

> 签名还原里 90% 的失败是「漏字段」和「排序错」,不是算法难。

## 四、常踩的坑(精选自原库 42 技能坑清单)

- **长度字段字节序读错 → 后面全错位**:未知协议里长度字段大端小端都试一遍,用「长度值 ≤ 实际载荷」裁定;解析器里显式写网络序。
- **把校验和当业务数据解**:包尾 2-4 字节对载荷变化敏感的,先假设是 CRC/校验,别当字段。
- **心跳当业务**:固定周期的小包是心跳,单列出来,不然状态机多出假分支。
- **重放被拒**:协议带递增 seq/nonce,还原时要**正确推进**,不能重发同一帧。
- **只读序列化函数、不看反序列化**:打包/解包可能不对称(条件字段、版本分支),**两个方向都读,对上了才是真布局**。
- **只有静态断言没有闭环**:还原的帧结构写个 client 发一帧,**服务端响应一致**才算成立 —— 这条和你的「真跑真拉」是同一条纪律。
- **验证码类从 Verify 接口反推**:真正提交的数据全封装在一个字段里,算法只是最后一步;核心是**输入完全一致,而不是算法等价**(明文一致了加密是最简单的一步)。
- **协议化时漏算额外签名层**:Verify 之外页面 SDK 还会自动加一层保护签名,先列全「所有非手工字段」再实现。
